# Smart Engagement V1: code audit and fixes

**21/10/2026 · audited the uncommitted implementation behind [17-engagement-implementation.md](17-engagement-implementation.md); fixes are local and uncommitted.** Nothing was deployed and no flags were changed. Every engagement flag still defaults off and `config/engagement.approved` is still false, so no user has been affected.

Three reviews ran in parallel: the server engine, the sources and observers, and the mobile client. The P0 findings and the main P1 findings were then checked again directly against the code. The fixes come with regression tests, listed below.

## Verified as claimed

These claims from doc 17 hold in the code:

- **Fail-closed policy.** A missing or malformed policy falls back to `approved: false`, and every flag requires `approved`. A malformed policy is still not covered by a test.
- **Atomic account-wide reservation.** All reads happen before any write. The family marker uses `tx.create`.
- **Ambiguous sends are never retried.**
- **Caps.** 1 per rolling 24 h and 3 per 7 days, with no off-by-one.
- **Expiry.** Quiet hours, snooze and spacing expire past the window instead of catching up.
- **Kill switches.** They are checked again just before handoff.
- **Callable authorization.** The owner uid must match, live membership and fences are checked, and ids are zod-validated.
- **Rules.** Engagement collections are denied by default, and the three settings docs are excluded from client reads.
- **Privacy.**
  - Push copy and data carry no child name, DOB or caption.
  - Prefs keys hold only uid and babyId.
  - There is no logging.
- **Dates.** The milestone date math holds for month-end and 29 February dates. The recap week runs Monday to Monday in the baby's zone.
- **Translations.** vi and en have the same 20 `eng*` keys.
- **Care notifications.** `cancelEngagementLegacy` never touches Care notifications.
