# Lumi time to card — 2026-10-19 (slice L2)

Slice L2 of [`docs/product/lumi-plan.md`](../product/lumi-plan.md) §4.4 (D-088, P-167 #4, #8, #9).
Target: a routine typed log ("bé bú 120ml lúc 8h", "thay tã ướt", "bé ngủ lúc 9h", "hút 100ml",
"bé nặng 5,2kg") shows its card in **≤ 1.5 s p50 / ≤ 3 s p95** warm. What changed is in
[`api.md`](api.md) "Lumi L2".

## What a typed log costs

| Step                      | Before L2                                                           | After L2                                                                                                     |
| ------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Callables from the phone  | 3: `quoteTask` → `startTask` → `getAssistantTask`                   | **1**: `startTask` (answers with the whole snapshot)                                                         |
| Firestore trigger hop     | 1 (`runAssistantTask` on the task write; its own cold start)        | **0** for text (the worker runs inside `startTask`)                                                          |
| Model call (gpt-4.1-mini) | every log (p50 ≈ 2.2–2.4 s)                                         | **none** for a routine log (rules); only what the rules leave                                                |
| Sequential reads          | ≈ 12 (scope, consent, model gate, pool, conversation; worker again) | scope / quote / consent / thread together; worker reuses them; the 4 planner reads run beside the model call |
| Credits                   | 1                                                                   | **0** for a rule-read log ("0 lượt · không tính")                                                            |
| Cold starts               | up to 4 functions; no warm-up                                       | `warmAssistant` every 5 min, 06:00–23:59 Asia/Ho_Chi_Minh                                                    |

## Measurements

**1. Network and cold start on dev** (unauthenticated POST from the owner's Mac in Vietnam to
asia-southeast1, before and after the deploy):

| Call                                                 | Cold                                       | Warm        |
| ---------------------------------------------------- | ------------------------------------------ | ----------- |
| `quoteTask` / `startTask` / `getAssistantTask` (401) | 2.9–3.7 s (one cold `startTask` hung 46 s) | 0.19–0.38 s |
| warm-up ping (`{ warmup: true }`, 200), after deploy | —                                          | 0.19–0.29 s |

Before L2 a log made 3 callables and a trigger, so up to four cold starts (≈ 3 s each) could stack
on top of the work below; after L2 one function serves the log and is pinged every 5 minutes.

**2. Server work, before vs after** (`firebase/tests/assistant-e2e/latency.ts`: the real callables and
worker on the Firestore emulator, a fake model that answers after 2.4 s — the live p50 —, + 220 ms
per callable round trip and 600 ms for the trigger's dispatch; 8 routine phrases and 2 that only the
model reads, 3 rounds each):

| Message                      | Before p50 | Before p95 | After p50  | After p95  |
| ---------------------------- | ---------- | ---------- | ---------- | ---------- |
| Routine log (rules)          | 3 765 ms   | 3 812 ms   | **265 ms** | **283 ms** |
| Model-read log (two events…) | 3 760 ms   | 3 768 ms   | 2 684 ms   | 2 685 ms   |

The emulator's reads are local (≈ 1–3 ms against ≈ 5–30 ms on Firestore in the region), so real
numbers are higher by roughly the read count × that difference — about 0.3–0.6 s for the routine
path, which keeps it inside 1.5 s p50 when warm. Cold, add one start (≈ 3 s) instead of up to four.

**3. Live model** (20 model-path cases touched by the prompt trim: multi-item, English, corrections,
reminders, expenses, voice run-ons; `--mode live --max-calls 25`): **20/20 pass**, 20 calls,
87 603 prompt + 5 100 completion tokens ≈ **US$ 0.04** at the `gpt-4.1-mini` list price; latency p50
2 166 ms, p95 12 000 ms (one slow call of 20 — the reason an inline run hands a long call to the
trigger instead of failing). The trim drops ≈ 1 950 characters (≈ 12 %) from a plain care log's
request (no calendar, no categories).

**4. Per-hop timings on dev** come from the `assistant timing` log lines (runbook §4). No family used
Lumi on dev between the deploy and this report, so device numbers are still to be read: send the
five routine phrases above from the dev app, then run the runbook's `gcloud logging read` and add
p50 / p95 per `path` here.

## Not done in L2

- `max_completion_tokens` is 1 100, not the plan's 400: the strict schema writes every field of every
  item (≈ 170 tokens an item), so 400 would cut a 3-feed reply; the cap does not slow a shorter one.
  The model's real lever is the output size: a compact per-kind schema would cut most of it (needs a
  new prompt version and a live run).
- The optimistic card on the phone (§4.4 last bullet) is not built: with rules the server card comes
  back in ≈ 0.3–0.6 s warm.
- Batches of routine logs ("8h bú 120ml, 11h bú 150ml") still go to the model.
