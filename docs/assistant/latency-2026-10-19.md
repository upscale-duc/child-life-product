# Lumi time to card — 2026-10-19 (slice L2)

Slice L2 of [`docs/product/lumi-plan.md`](../product/lumi-plan.md) §4.4 (D-088, P-167 #4, #8, #9).
Target: a routine typed log ("bé bú 120ml lúc 8h", "thay tã ướt", "bé ngủ lúc 9h", "hút 100ml",
"bé nặng 5,2kg") shows its card in **≤ 1.5 s p50 / ≤ 3 s p95** warm. What changed is in
[`api.md`](api.md) "Lumi L2".

## What a typed log costs

| Step                      | Before L2                                                           | After L2                                                                                                     |
| ------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Callables from the phone  | 3: `quoteTask` → `startTask` → `getAssistantTask`                   | **1**: `startTask` (answers with the whole snapshot)                                                         |
| Firestore trigger hop     | 1 (`runAssistantTask` on the task write; its own cold start)        | **0** for text (the worker runs inside `startTask`)                                                          |
| Model call (gpt-4.1-mini) | every log (p50 ≈ 2.2–2.4 s)                                         | **none** for a routine log (rules); only what the rules leave                                                |
| Sequential reads          | ≈ 12 (scope, consent, model gate, pool, conversation; worker again) | scope / quote / consent / thread together; worker reuses them; the 4 planner reads run beside the model call |
| Credits                   | 1                                                                   | **0** for a rule-read log ("0 lượt · không tính")                                                            |
| Cold starts               | up to 4 functions; no warm-up                                       | `warmAssistant` every 5 min, 06:00–23:59 Asia/Ho_Chi_Minh                                                    |

| Model-read log (two events…) | 3 760 ms   | 3 768 ms   | 2 684 ms   | 2 685 ms   |

trigger instead of failing). The trim drops ≈ 1 950 characters (≈ 12 %) from a plain care log's

**4. Per-hop timings on dev** come from the `assistant timing` log lines (runbook §4). No family used

## Not done in L2

- `max_completion_tokens` is 1 100, not the plan's 400: the strict schema writes every field of every
  item (≈ 170 tokens an item), so 400 would cut a 3-feed reply; the cap does not slow a shorter one.
  The model's real lever is the output size: done in §5 (compact per-kind output, prompt v7).
- The optimistic card on the phone (§4.4 last bullet) is not built: with rules the server card comes
  back in ≈ 0.3–0.6 s warm.
- Batches of routine logs ("8h bú 120ml, 11h bú 150ml") still go to the model.

## 5. Compact model output (prompt `assistant-extract-v7`, same day)

What still waits on the model after L2 — multi-item batches, expenses, reminders, corrections,
English — paid for output it did not need: the strict schema made every item spell out all 23
fields (mostly `null`). v7 gives each intent kind its own strict branch with only the fields the
planner reads for it (`intentKindFields` in `firebase/functions/src/assistant-model.ts`), writes
`correctsPrevious` only when a previous turn travels, and `parseExtraction` fills the other fields
with `null`, so `planTextIntents` and the worker read the same extraction (a v6 reply still parses).
`api.md` "Lumi L2" has the shape.

**Live, `gpt-4.1-mini`, the same 20 model-path cases as §3** (`--mode live`, isolated emulator):

| Run (UTC, 2026-10-19)                                                      | Cases | Calls | Prompt tokens a call | Completion tokens a call | Model p50    | Model p95 |
| -------------------------------------------------------------------------- | ----- | ----- | -------------------- | ------------------------ | ------------ | --------- |
| v6 (§3, 05:58)                                                             | 20/20 | 20    | 4 380                | 255                      | 2 166 ms     | 12 000 ms |
| v7, first cut (per-kind enums, field descriptions; 06:14)                  | 20/20 | 20    | 5 871                | **133** (−48 %)          | **1 573 ms** | 2 368 ms  |
| v7 as shipped (shared `$defs`, no field descriptions; 12 of the 20, 06:18) | 12/12 | 12    | 5 288                | 148                      | 1 578 ms     | 1 887 ms  |

The 12 cases of the last run are the heavier half (multi-item, expenses, reminders, a correction,
English: `mi-01/02/05/08/09/11`, `ex-01/04/12`, `rm-01/02`, `bot-17`); their per-case time (all
steps, mostly the model call) has a median of 2 812 ms with v6, 1 879 ms with the first cut and
1 995 ms as shipped. Every case gave the same outcome as with v6. The v6 p95 was one slow call
(12 s, `mi-08`); the runs were 15–20 minutes apart from the same Mac, so provider load may differ a
little.

**The schema is counted as input.** Probes with one message ("6h bú 90ml, 9h bú 120ml", every
kind allowed, no previous turn, a 1-token answer) give the prompt tokens of each schema layout:

| Schema                                                       | Prompt tokens |
| ------------------------------------------------------------ | ------------- |
| v6 (one flat item, 23 fields)                                | 4 214         |
| v7 first cut (per-kind evidence / uncertain / missing enums) | 5 659         |
| … without the field descriptions                             | 5 484         |
| … evidence / uncertain / missing as shared `$defs`           | 5 184         |
| **… both (shipped)**                                         | **5 009**     |
| … and every field value as a `$ref` too                      | 5 276         |

So v7 costs ≈ 800 more input tokens a call and saves ≈ 120 output tokens. At the list price
(US$ 0.40 / M input, 1.60 / M output) an uncached call is ≈ 6 % dearer (≈ US$ 0.0023 against
0.0022); the system prompt and the schema are the same prefix for every call with the same
allowlists, and OpenAI's prompt cache bills that part at a quarter when calls are minutes apart (a
warm v7 call showed 4 992 of 5 659 prompt tokens cached). Prefill of 800 tokens is far cheaper in
time than 120 generated ones, which is where the ≈ 0.6 s comes from.

**Spend for §5:** 32 live e2e calls (180 874 prompt + 4 446 completion tokens) and 6 one-token
probes (≈ 31 000 prompt tokens) ≈ **US$ 0.09**.

**Tests:** functions unit 424 / 424 (+ 1 skipped), including the per-kind branches, the `$defs`, a
compact item that reads as the full v6 one and stays strict; fake e2e 280 / 281 (`ga-11` as
before) both with v6-shaped and with v7-shaped fake replies — the harness now writes only each

**Kept as is:** `max_completion_tokens` 1 100 (a cap does not slow a shorter reply, and it leaves
